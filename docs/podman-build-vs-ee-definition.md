# Hand-written Containerfile + `podman build` vs. an EE definition

Many teams build execution environments (EEs) by keeping a Containerfile,
originally generated by an old ansible-builder and edited by hand since,
and running `podman build`. This page builds **the same EE both ways**, from
the same base image with the same contents, and measures the difference.

* **Legacy:** [`examples/legacy-podman-build/`](../examples/legacy-podman-build/),
  a real-world hand-maintained Containerfile with identifying details removed.
* **Recommended:** [`ee_definitions/examples/ee-winrm-kerberos-rhel8_v1.0.0.yml`](../ee_definitions/examples/ee-winrm-kerberos-rhel8_v1.0.0.yml),
  built by this repo's `build_ee.yml` (ansible-builder 3 via `infra.ee_utilities`).

Both produce a Windows-automation EE: `pywinrm` with Kerberos, `kinit`,
`git`, a corporate CA, `pip.conf` and `krb5.conf`.

---

## TL;DR

| | Legacy `podman build` | EE definition (this repo) | Difference |
| :-- | --: | --: | :-- |
| **Image size** (uncompressed) | 556 MB | **370 MB** | **−186 MB (−33%)** |
| **Pull size** (gzip, approx.) | 189 MB | **123 MB** | **−66 MB (−35%)** on every node that pulls it |
| **Build time** (no cache, average) | 47 s | **36 s** | **−23%**, even including Ansible's own overhead |
| **Layers** | 14 | **5** | Simpler, faster to pull |
| **Runs as** | **root** ⚠️ | uid 1000 | Non-root by default |
| **Compiler and headers shipped** | gcc, krb5-devel, Python 3.6 devel | none | 39 fewer packages in production |
| **Same functionality** | ✅ | ✅ | All 7 functional checks pass on both |

Removing the build-only packages entirely is valid for this base image (see
[finding 1](#1-the-compiler-was-never-needed)). That brings the build down to
**29 s (−38%)**, with an identical 370 MB image.

## What was compared

| | Legacy | Recommended |
| :-- | :-- | :-- |
| Definition | `Containerfile` + `bindep.txt` + `requirements.txt` + hidden `_build/scripts/` | One YAML file |
| Build command | `podman build -f Containerfile .` | `ansible-playbook build_ee.yml -e ee_file=...` (or an AAP job template) |
| Base image | `ansible-automation-platform-24/ee-minimal-rhel8:1.0.0-965` (311 MB, 191 RPMs) | same |
| Python packages | `jmespath==1.0.0`, `requests>=2.20`, `pywinrm[kerberos]` | same |
| System packages | gcc, krb5-devel, krb5-libs, krb5-workstation, python3-devel, git | same, but build-only ones tagged `[compile]` |
| Corporate CA, `pip.conf`, `krb5.conf` | added in builder **and** final stages | CA + `pip.conf` once in base, `krb5.conf` in final |

### Method

* `examples/legacy-podman-build/compare.sh` built each variant **2 rounds,
  with caching disabled** (`podman build --no-cache`), base image pre-pulled,
  on the same host (rootless podman, ansible-builder 3.1.1, ansible-core 2.20).
* Legacy build time is `podman build` wall-clock time. Recommended build
  time is the **whole `ansible-playbook` run**: validation, rendering,
  ansible-builder and cleanup. The comparison is deliberately biased
  *against* the recommended way.
* Sizes come from `podman image inspect`. Pull size is `podman save | gzip`,
  which approximates the compressed registry transfer.
* The same 11 checks ran inside every image (results [below](#detailed-results)).

### Build-host substitutions (legacy build only)

The legacy Containerfile only builds on a **subscribed RHEL host**: it
deletes the UBI repo file, and two of its packages are only in RHEL repos.
To build it on a plain podman host, `compare.sh` makes three substitutions,
chosen to reproduce what it gets on RHEL:

| Original | Substitution | Why it's faithful |
| :-- | :-- | :-- |
| `RUN rm -f /etc/yum.repos.d/ubi.repo` | keep `ubi.repo` | Needs *some* repo. The same RPMs come from UBI instead of RHEL. |
| `python3-devel` | `python36-devel` | That's what `python3-devel` resolves to on RHEL 8 |
| `git-subtree` | `git` | `git-subtree` is RHEL-only. It's a small add-on to `git`, so size impact is negligible. |

The recommended definition needed no substitutions. It builds on any
podman host.

### Where the extra 186 MB comes from

Every package in the recommended image is also in the legacy image. The
legacy image additionally ships **39 RPMs (178 MB installed)** that are
only needed to compile software:

| Extra in legacy image | Packages | Installed size |
| :-- | --: | --: |
| C compiler toolchain: gcc, cpp, binutils, glibc-devel, kernel-headers, … | 10 | 127.7 MB |
| Python 3.6 stack pulled in by `python3-devel` | 15 | 44.8 MB |
| krb5-devel and its `-devel` / pkgconf dependencies | 13 | 4.8 MB |

## Why the recommended way wins

### Measured

1. **Smaller images: build tools stay in the build.** In a generated
   ansible-builder build, system packages without a bindep profile are
   installed in the builder stage **and** shipped in the final image.
   Tagging build-only packages `[compile]` keeps them in builder:
   ```yaml
   - gcc [platform:rpm compile]
   - krb5-devel [platform:rpm compile]
   ```
   Result: **−186 MB**, and no compiler in production, which also reduces
   the attack surface and the CVE scan findings.
2. **Faster builds.** The legacy file installs the full package set twice,
   once in builder and again in final, and creates 14 layers. The recommended
   build installs runtime packages only once in final and squashes new layers
   (`--squash=new`). That's **−23%**, even with Ansible's own overhead
   included.
3. **Non-root by default.** ansible-builder ends the image with
   `USER 1000` and sets up permissions for OpenShift's arbitrary UIDs. The
   legacy file never switches back from `USER root`, so the image's
   **default user is root**. Jobs run as root inside the container unless
   the runtime overrides the user.

### Findings while converting

#### 1. The compiler was never needed

This base image **already ships `pywinrm` 0.4.1, `pykerberos` 1.2.1 and
`requests` 2.25.0**. The legacy build installs only `jmespath`, which is pure
Python, so `gcc`, `krb5-devel` and `python3-devel` compile **nothing**. They
just add 178 MB. The *ours-lean* variant drops them: same 370 MB image,
**29 s** builds. The recommended definition keeps them, tagged `[compile]`,
so it stays safe if a future base image stops bundling those libraries.

#### 2. `python3-devel` provided headers for the wrong Python

On RHEL 8, `python3-devel` provides **Python 3.6** headers, but this base
image runs **Python 3.9**. Had anything needed compiling, the build would
have failed or produced a broken module. It never surfaced only because of
finding 1. The recommended definition names the matching package,
`python39-devel`.

#### 3. An unpinned base image made builds unreproducible

The original pulled `ee-minimal-rhel8:latest` from an internal mirror. Two
builds of the same Containerfile could produce different EEs: a different
Python, different bundled libraries, and finding 1 silently changing. The
recommended definition pins a tag, and the filename carries the EE's own
version (`_v1.0.0`).

#### 4. Hidden, frozen generated files

The Containerfile depends on `_build/scripts/` (`introspect.py`, `assemble`,
…). These were generated by **ansible-builder 3.0.x**, which uses
`requirements-parser` and `--sanitize`, and were never updated. Bug fixes and
features in later ansible-builder releases never reach this build, and anyone
who loses those files can't rebuild. The recommended approach regenerates
everything on each build from the installed ansible-builder.

#### 5. No collections stage

The legacy file has no galaxy stage, so **no Ansible collections can be
added** without hand-writing more Containerfile. In the definition it's
three lines under `dependencies.galaxy`. ansible-builder then also installs
each collection's own Python and system requirements automatically.

#### 6. Duplicated configuration

The CA certificate, `pip.conf` and repo changes are repeated in both the
builder and final stages, so they're easy to update in one place and forget
in the other. The recommended definition sets them **once** in
`prepend_base`, which every stage inherits (see
[ansible-builder stages](ansible-builder-stages.md)).

#### 7. Only builds on a subscribed RHEL host

Deleting `ubi.repo` and depending on RHEL-only packages means the legacy file
fails on any other podman host, including CI runners. The recommended
definition builds anywhere with podman. If you do need RHEL-only packages,
it's an explicit, documented choice.

### Workflow (not measured, just as real)

| | Legacy | Recommended |
| :-- | :-- | :-- |
| What you maintain | Containerfile + 2 dependency files + generated scripts | One YAML file per EE |
| Versioning | Manual `podman tag` | Version is in the filename, pushed as `:<version>` + `:latest` |
| Where it's pushed | Manual `podman push` | `destination:` in the file, with per-registry credentials |
| Review | Containerfile diffs | Small, readable YAML diffs in merge requests |
| Safety checks | none | Fails the build if Ansible, ansible-runner or ansible-galaxy are broken |
| Running builds | Shell on a build host | CLI **or** an AAP job template with a survey, audited and with RBAC |
| Secrets | Files in the build context | Vault or AAP credential. The hub token never lands in the image. |

## Converting a Containerfile like this one

| Legacy Containerfile / files | EE definition |
| :-- | :-- |
| `ARG EE_BASE_IMAGE=...:latest` | `base_image:` with a **pinned** tag |
| `requirements.txt` | `dependencies.python:` |
| `bindep.txt` | `dependencies.system:`, with build-only packages tagged `[compile]` |
| *(collections, if any)* | `dependencies.galaxy.collections:` |
| `ADD ca-bundle.crt ...` + `update-ca-trust` (per stage) | `build_items` / `build_files` + one `prepend_base` step |
| `ADD pip.conf /etc/pip.conf` (per stage) | one `prepend_base` step |
| `COPY krb5.conf /etc/krb5.conf` (final) | `append_final` step |
| `RUN rm -f /etc/yum.repos.d/ubi.repo` | Only if you truly need RHEL-only packages. Keep UBI otherwise. |
| `_build/scripts/*` | *(nothing: regenerated on each build)* |
| `podman build`, `podman tag`, `podman push` | `build_ee.yml`, using the filename for version and `destination:` |

## Reproduce it

On the EE Builder VM, from the repo root:

```bash
podman login registry.redhat.io
ROUNDS=2 examples/legacy-podman-build/compare.sh | tee compare-results.md
```

Absolute times depend on the host and network, so expect different seconds
but similar ratios. The size difference doesn't depend on the host at all.
